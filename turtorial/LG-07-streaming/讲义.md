# LG-07：流式输出 —— 把「等结果」变成「看过程」

**目标学员**：已掌握 StateGraph 和预构建 Agent（LG-01～LG-06），想做实时交互式 AI 应用的开发者。

**核心冲突句**：
> `invoke()` 是个黑盒——用户发问后只能盯着白屏干等，中间每个节点执行、每个 token、每次进度全被盖住。流式不改变图做什么，只改变你「怎么看」它：让过程实时推送到用户眼前。

**学完能做什么**：
- 按需求选对 5 种主力 `stream_mode`（values / updates / messages / custom / tasks）
- 用真实 LLM 跑出 token 级打字机效果
- 组合多种模式，处理子图嵌套的事件层级

**一条贯穿全章的准确性底线**：
> 稳定版 `stream(stream_mode=...)` **直接 yield 裸数据**。`values` 给 State、`updates` 给 `{节点:输出}`、`custom` 给你推的负载、`tasks` 给任务 dict。**不要去 `chunk["data"]` / `chunk["ns"]` 里找**——那是另一套实验 API（v3 typed / `astream_events`）的信封，本章不用，混用会直接 `KeyError`。

---

## 0. 开篇：为什么需要流式（人类直觉先行）

### 要讲清楚的问题

不要从 `stream_mode` 参数开场。先让学生意识到「黑盒等待」的痛，再说流式是来解决它的。

### 人类直觉

点外卖最焦虑的不是等 30 分钟，而是不知道「外卖到哪了」。平台给你显示「商家接单 → 骑手到店 → 已取餐 → 距你 500 米」，等待时间没变，焦虑没了——因为你看到了过程。

### 模型反差

我们前面的图都是黑盒：`graph.invoke(input)`，等几秒甚至几十秒，蹦出一个最终结果。这几十秒用户完全不知道发生了什么。`graph.stream(...)` 不改变图做什么，只把中间过程一条条交给你。

### 配图

使用 `images/blackbox-vs-stream-cn.svg`：左边 invoke 黑盒（用户白屏干等），右边 stream 透明盒（实时看到节点执行 / token / 进度），底部一句「invoke 等一个结果，stream 看整个过程」。

## 1. 全景：先用一张图把选型定下来

### 要讲清楚的问题

`stream_mode` 有 7 个取值，但日常就 5 个主力 + 2 个调试档。先整体，再逐个拆。

### 配图

使用 `images/stream-modes-overview-cn.svg`：粒度轴「粗 → 细」串起 values / updates / tasks / messages，custom 标为「旁路（你主动推）」，下方是调试档（checkpoints / debug）和两条通用规则（组合 `(mode, chunk)`、子图 `(ns, chunk)`）。

### 选型表

| 模式 | 何时推送 | 推送什么（裸数据，直接拿） | 典型用途 |
|---|---|---|---|
| `values` | 每个超级步结束 | 完整 State（一个 dict） | 状态面板、节点高亮 |
| `updates` | 每个超级步结束 | `{节点名: 该节点返回}` | 省带宽的增量更新 |
| `messages` | LLM 每个 token | `(消息块, metadata)` 元组 | 打字机效果（本章重点） |
| `custom` | 节点里调 `writer()` | 你推的任意数据 | 进度条、业务通知 |
| `tasks` | 每个节点 起 / 止 | 任务 dict（名字、耗时、error） | 执行监控、错误捕获 |
| `checkpoints` / `debug` | 检查点 / 全量 | 调试用，数据量大，平时不开 | 排查执行流程 |

### 教学要点

反复强调「裸数据」原则，这是后面所有代码不踩坑的前提。

## 2. 准备：一个最小演示图

### 要讲清楚的问题

`values` / `updates` / `tasks` 这几种「看结构」的模式不需要 LLM，先用一个纯函数的小图演示，便于聚焦机制。

### 推荐演示

搭一个 `WriterState` 图：`plan_outline` 和 `gather_sources` 从 `START` 并行出发，都完成后进 `generate_content`。并行 + 顺序刚好能看出各模式的差异。模型配置从 `streaming_demo_support` 导入（读 `.env`），留给第 5 节用。

### 教学要点

不要用 `draw_mermaid_png()`（要联网）；打印节点名作为「图已就绪」的证据即可。

## 3. `values`：每步推一份完整 State 快照

### 要讲清楚的问题

每个超级步结束推一次当前完整 State，`stream(stream_mode="values")` 直接 yield 那个 State dict。适合状态面板：每来一帧刷新整个视图。

### 证据输出

```text
stream_mode='values' —— 每帧都是完整 State：
第 0 帧已填字段: ['topic']
第 1 帧已填字段: ['topic', 'outline', 'sources', 'log']
第 2 帧已填字段: ['topic', 'outline', 'sources', 'content', 'log']
```

### 教学要点

每帧都是**完整** State，不是增量；State 大时带宽不省（引出 updates）。

---

## 4. `updates`：只推「哪个节点、返回了什么」

### 要讲清楚的问题

`values` 给整盘，`updates` 只给这一步的增量，形状是 `{节点名: 节点返回值}`。State 大、只关心变化时用它。

### 证据输出

```text
节点 gather_sources   更新了: ['sources']
节点 plan_outline     更新了: ['outline']
节点 generate_content 更新了: ['content']
```

### 教学要点

并行节点同步触发时各自出现；前端拿到增量后要自己 merge 进现有 State。

---

## 5. `messages`：LLM 每个 token 实时蹦出（本章重点）

### 要讲清楚的问题

这是打字机效果的核心。`stream(stream_mode="messages")` yield 的是 **`(消息块, metadata)` 元组**——直接解包，不是 `chunk["data"]`。`metadata` 标明 token 来自哪个节点、第几步。

### 推荐演示

接**真实 LLM**（读 `.env`）：建一个 `MessagesState` 图，节点里 `chat_model.invoke(state["messages"])`，然后 `stream_mode="messages"` 逐 token 打印。

```python
for token, metadata in chat_graph.stream(inputs, stream_mode="messages"):
    print(token.content, end="", flush=True)  # 追加，不是替换
```

### 证据输出

逐字蹦出的真实回答 + 末尾「这些 token 来自节点: writer（第 1 步）」。

### 教学要点（两个必记）

1. **token 是增量，前端要「追加」不是「替换」**：`text += token.content`。写成 `text = token.content` 只剩最后一个字——最常见的 bug。
2. **只有走 LLM 的输出才有 token**：节点里直接 `return "字符串"`（不经过 ChatModel）不会触发 `messages`。

---

## 6. `custom`：你在节点里主动推任意进度

### 要讲清楚的问题

前面几种是 LangGraph 自动推的；`custom` 是**旁路**：你在节点里拿 `writer`，想推什么推什么。`stream(stream_mode="custom")` yield 的就是**你推的那个对象本身**。

### 推荐演示

`writer = get_stream_writer()`，循环里 `writer({"stage":..., "source":..., "percent":...})`。消费端直接 `event["percent"]`，没有外层信封。

### 证据输出

```text
[搜索] 财经数据   25%
[搜索] 新闻     50%
[搜索] 竞品     75%
[搜索] 专家观点   100%
```

### 教学要点

`writer` 必须在**节点函数内部**调用；只有 `stream_mode` 含 `custom` 时这些推送才流出来。

---

## 7. `tasks`：每个节点的「开始 / 结束」自动追踪

### 要讲清楚的问题

不用手动推，LangGraph 在每个节点 start / finish 各推一次裸 dict。区分开始/结束就看有没有 `result` 键；两次时间差即耗时；失败时 `error` 自动带上——天然适合监控和错误捕获。

### 证据输出

```text
▶ 开始  gather_sources
✓ 完成  gather_sources  (耗时 0.1 ms)
✓ 完成  plan_outline    (耗时 0.2 ms)
▶ 开始  generate_content
✓ 完成  generate_content (耗时 0.1 ms)
```

### 教学要点

`tasks` 是「系统自动、节点级」；`custom` 是「你手动、任意粒度」。两者互补，别混。

---

## 8. `debug` / `checkpoints`：调试档，知道有就行

### 要讲清楚的问题

`debug` 把每一步都吐出来，形状是 `{"step", "timestamp", "type", "payload"}`，`type` 是 `task` / `task_result` / `checkpoint`，数据量大，**生产别开**。`checkpoints` 配合状态恢复调试。选型用不到，看一眼结构即可。

### 教学要点

提醒一个易错点：`debug` 事件里的 `payload['name']` 才是节点名；`ev['type']` 是 `task`/`task_result`，**不是** `'debug'`（旧讲法 `if chunk["type"]=="debug"` 永远为假）。

---

## 9. 组合多种模式：一次拿到打字机 + 进度条

### 要讲清楚的问题

真实 UI 常常既要打字机（`messages`）又要进度条（`custom`）。`stream_mode` 传一个**列表**即可，代价是每条事件变成 **`(mode, chunk)` 元组**，要先解包再按 `mode` 分流。

### 证据输出

```text
[tasks]  combo 开始
[custom] 进度 0%
[custom] 进度 50%
[custom] 进度 100%
[tasks]  combo 完成
```

### 教学要点

忘了解包是高频坑：列表模式每条是 `(mode, chunk)`，不是单值。

---

## 10. 子图嵌套：用 `subgraphs=True` 看进子图内部

### 要讲清楚的问题

用 `create_supervisor` / `create_swarm`（LG-06）或手动把子图当节点时，图是嵌套的。默认 `stream()` 只给顶层事件，子图内部是黑盒。加 `subgraphs=True`，子图事件也流出来，代价是每条事件前面多一截 namespace，变成 **`(ns, chunk)` 元组**。

### 推荐演示

为了可离线运行，用纯函数搭「父图把子图当节点」，对比开关 `subgraphs=True` 前后的事件。

### 证据输出

```text
默认：只看到顶层
   {'parent_step': {'x': 10}}
   {'child': {'x': 11}}

subgraphs=True：每条变 (ns, chunk)
  [顶层图] ns=()  {'parent_step': {'x': 10}}
  [子图 child] ns=('child:<内部id>',)  {'child_step': {'x': 11}}
  [顶层图] ns=()  {'child': {'x': 11}}
```

### 教学要点

`ns` 形如 `("child:<内部id>",)`，冒号前是子图所在的**节点名**。前端就靠 `ns` 决定「这条放主面板还是子图详情面板」。这条 `ns` 在 LG-08 多 Agent 时会被用来画执行时间线。

## 11. 工程化：什么该流、什么不该流（够用就好）

### 要讲清楚的问题

流式不是越多越好。一个原则定大方向：**人读的东西流式，机器读的东西非流式。**

| 输出 | 流式？ | 为什么 |
|---|---|---|
| LLM 自然语言内容 | ✅ 流 | 消除等待焦虑，提升体感速度 |
| 工具调用参数 / 结果 | ✗ 不流 | 结构化数据，碎片无意义 |
| 错误 / 中断审批 | ✗ 不流 | 要立即、完整呈现，供用户决策 |
| 进度通知 | ✗ 不流 | 一次推送状态即可（用 `custom`） |

### 教学要点

SSE / WebSocket 协议、消息信封字段是**前端工程**的事，不属于 LangGraph 机制，按各自前端框架落地即可，本课不展开（避免把课程变成前端手册）。

## 12. 常见误区

| 坑 | 现象 | 纠正 |
|---|---|---|
| 去 `chunk["data"]` 取数据 | `KeyError` / 取不到 | 稳定版直接给裸数据：values 是 State，custom 是你推的 dict，tasks 是任务 dict |
| 用 `values` 做打字机 | 每帧整盘 State，要 diff | 打字机必须用 `messages` |
| token 用「替换」 | 只显示最后一个字 | `text += token.content`，不是 `text = ...` |
| `custom` 的 `writer` 没在节点里 | 没有任何自定义事件 | `writer` 必须在节点函数内部调用 |
| 嵌套子图看不到内部 | 只有顶层事件 | 加 `subgraphs=True`，按 `(ns, chunk)` 区分来源 |
| 组合模式忘解包 | 不知道是哪种 mode | 列表模式每条是 `(mode, chunk)` |

### 调试技巧

拿不准某模式 yield 什么，**先别接前端**，直接 `for chunk in graph.stream(..., stream_mode=X): print(type(chunk), chunk)` 看真实形状。

## 13. 小结

把黑盒 `invoke` 换成 `stream`，就是把「等一个结果」变成「看整个过程」。选哪种过程看你要给用户什么反馈：

```text
看 LLM 逐字生成   → messages
要进度百分比      → custom（节点里 writer()）
要节点起止/耗时   → tasks
要当前 State 全貌 → values
只要增量、省带宽  → updates
看子图内部        → 任意模式 + subgraphs=True
既要打字机又要进度 → stream_mode=["messages", "custom"]
```

记忆口诀：

> **values 看全局，updates 看变化，messages 看逐字，custom 看进度，tasks 看生命周期，subgraphs=True 看嵌套。**

共同前提一句话：**稳定版 stream 直接给裸数据，组合加 (mode, …)，子图加 (ns, …)。**
