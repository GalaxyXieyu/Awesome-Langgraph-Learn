# LG-06：预构建 Agent —— 你反复手搓的那几张图，LangGraph 已经封装好了

> 核心冲突句：**你已经会用 StateGraph 手搓图了；但“能调工具的 Agent”“给 Agent 加限次 / 脱敏 / 审批”“多专家协作”这几张图你会反复搭。LangGraph 把它们封装成预构建件——直接用，别再手搓；只有超出标准件时，才回到自定义图。**

这节课从一个真实产品场景开始：**OpsBot 客服 / 运维助手**。

> 用户问：“查一下订单 A100 的状态，如果符合规则，帮我估算退款金额。”
>
> 这个需求看起来简单，但背后的图结构是高度标准化的：模型判断要查订单、查政策、算退款；工具返回结果；模型再整合回复。
>
> 如果每次都从零写 StateGraph：agent 节点、tools 节点、条件边、循环边，会很繁琐。预构建件的价值就在这里：把这种反复出现的标准图提前搭好。

本节课要训练的判断不是“背 API”，而是：**哪些需求被预构建件覆盖了、可以直接拿来用；哪些超出了标准件、必须把控制权拿回来自定义图。**

## 0. 这一章在讲什么：LangGraph 替你封装好了哪些“图”

### 要讲清楚的问题

学生已经会用 `StateGraph` 手搓图。现在要先把全章主线立住：**LangGraph 把哪些反复手搓的图封装成了预构建件，各覆盖什么问题，什么才回到手搓。** `create_agent`（ReAct）只是其中一类，不要让它独占开场。

### 人类直觉

有几张图你会反复搭：一个“能调工具、看结果、再判断”的 Agent；给它加“最多调 3 次 / 敏感信息打码 / 长对话摘要 / 危险动作先问人”；让多个专家分工协作。这些结构高度标准化，没必要每次从零连节点和边。

### 预构建件全景（三类 + 一个边界）

```text
① 标准 Agent 循环   → create_agent            覆盖：模型调工具→看结果→再判断（ReAct）
② 横切关注点         → middleware 全家桶        覆盖：限次 / 重试 / 摘要 / 脱敏 / 审批
③ 多 Agent 协作      → create_supervisor/swarm  覆盖：主管分发 / 平级转接
边界（才手搓）        → 自定义 StateGraph         副作用审批 / 自定义状态字段 / 复杂业务分支
```

### 配图

使用 `images/prebuilt-landscape-cn.svg`。这张全景图把“预构建件覆盖哪三类问题、各省掉什么手搓、什么才回到 StateGraph”一次讲清，作为全章地图。

### 需求 → 预构建件对照表

| 你的需求 | 用哪个预构建件 | 替代了什么手搓 |
|---|---|---|
| 能查工具、循环判断的 Agent | `create_agent` | agent / tools 节点 + 条件边 + 循环边 |
| 限次 / 重试 / 摘要 / 脱敏 / 审批 | `middleware` 全家桶 | 塞 prompt 或手写拦截节点 |
| 多专家分发 / 平级转接 | `create_supervisor` / `create_swarm` | 手搓调度与交接路由 |
| 副作用审批 / 自定义状态 / 复杂分支 | 自定义 `StateGraph` | —— 这才是你该手搓的部分 |

### 推荐话术

> 预构建不是“更高级的图”，而是“你会反复手搓的那几张图，LangGraph 提前搭好了”。它求快、覆盖标准件；手搓求控、处理例外。后面每一节都落在这张全景图的某一格。

## 1. 模型配置：继续用真实 LLM

### 要讲清楚的问题

这一节的核心行为是“模型产生工具调用”。不能用硬编码模拟，否则学生看不到真实模型如何选择工具、如何产生 `tool_calls`、如何在工具结果后再次回答。

### 推荐演示

显式读取：

```text
OPENAI_MODEL
OPENAI_BASE_URL
OPENAI_API_KEY
OPENAI_TEMPERATURE
```

缺配置时直接报错，不做 fake fallback。

## 2. 先把外部能力原子化成 Tools

### 人类动作

客服会把能力拆开：查订单、查退款政策、计算退款金额。每个能力都可以被不同客服、不同流程复用。

### Agent 的限制

模型不能直接访问订单库或计算规则。你要把这些能力显式做成 tool，模型才能调用。

### 推荐演示

定义三个可控工具：

- `query_order_status(order_id)`
- `query_refund_policy(product_type)`
- `calculate_refund_amount(order_amount, shipping_cost)`

### 证据输出

```text
工具数量: 3
工具名称: [...]
能力是否已原子化: 是 — 这些工具可以被不同 Agent 复用
```

## 3. ①号预构建件：create_agent —— 标准 ReAct 循环

### 先理解这条循环为什么存在：AI 显得蠢，常因为少了工具和负反馈

不要直接把 ReAct 当既定事实。先讲它的由来：很多人觉得 AI 蠢，其实是拿一个被剥夺了工具和反馈的它，去比一个工具和反馈都齐全的人。

```text
人显得聪明：手里有很多工具（查资料、算一遍、问同事）+ 每步有负反馈（算错会发现、对方说“不对”会改）
        → 能不断试错、纠偏，凑出正确结果。
纯 LLM 蠢在哪：没工具（只凭记忆）+ 没负反馈（说完即止、不能回头）
        → 不是笨，是“一锤子买卖 + 没有手”。
```

`ReAct（Reason + Act）` 就是把这套逻辑还给模型：

```text
Reason（想下一步）→ Act（用工具动手）→ Observe（看结果，这就是负反馈）→ 再 Reason
      ↑___________________ 循环到模型认为做完 ___________________|
```

工具补上“手”，Observe 补上“负反馈”。`create_agent` 封装的就是这条标准循环，它的灵魂是“自主”：走哪条路由模型当场决定。

### 配图

使用 `images/control-autonomy-spectrum-cn.svg`。这张图把“纯 LLM → +Tools → ReAct → 图嵌 Agent”的演化线，和“什么时候该把控制权收回手搓”钉在同一条“控制力↔自主性”光谱上，正好顺带交代第 6 / 9 节的迁移边界。

### 人类动作

客服看到用户问题，会自然做：判断需要什么信息 → 查工具 → 看工具结果 → 回答用户。

### Graph 的限制

Graph 不会自然循环。你需要 agent 节点、tools 节点、条件边、循环边。预构建 Agent 帮你把这条标准循环搭好了。

### API 映射

```python
opsbot_agent = create_agent(chat_model, ops_tools, system_prompt=opsbot_prompt)
```

### 证据输出

```text
消息总数: 4+
是否产生 tool_calls: 是
工具消息数量: 3
最终回复: ...
```

### 教学要点

真实 LLM 决定调用哪些工具，预构建 Agent 负责把 tool call、tool execution、再思考循环串起来。

## 4. 白盒化：create_agent 内部到底帮你搭了什么

### 要讲清楚的问题

预构建不是魔法。它底层仍然是一张图，只是把常见结构封装了。

### 配图

使用 `images/react-loop-cn.svg`。

### 白话模型

```text
用户输入
  ↓
agent 节点调用 LLM
  ↓
如果 AIMessage 有 tool_calls → tools 节点执行工具 → 回到 agent
如果 AIMessage 没有 tool_calls → END
```

### 证据输出

通过打印 messages 链路观察：

```text
HumanMessage
AIMessage: tool_calls=3
ToolMessage: query_order_status
ToolMessage: query_refund_policy
ToolMessage: calculate_refund_amount
AIMessage: tool_calls=0
```

### 教学要点

循环是否继续，不看模型“说结束”，而看最后一条 AIMessage 是否还有 `tool_calls`。

## 4.5 源码白盒化：先看清结构图，再让 agent 自己确认

### 要讲清楚的问题

第 4 节用文字解释了循环，但学生还是会把 `create_agent` 当成黑盒。注意顺序：**先给一张「先整体、再拆解」的结构图建立心智，再用打印做证据**——不要一上来就 dump 节点、边、mermaid 文本，那样又丑又复杂，学生一看就放弃。

### 配图

使用 `images/create-agent-anatomy-cn.svg`：① 整体只有 `model` / `tools` 两个业务节点；② 单独拆解唯一难点——循环是否继续，看最后一条 `AIMessage` 还有没有 `tool_calls`；右下角埋下「加 middleware 只在 model 前后插节点」的伏笔。

### 推荐演示

1. 先展示结构图，把两层心智讲清楚。
2. 再打印 `opsbot_agent.get_graph()` 的节点和边，作为「图不是我编的」的运行证据，和结构图逐字对照。
3. `draw_mermaid()` 不在 notebook 里展开（原始 mermaid 文本对初学者更难读），只在讲义里留一句「想可视化可贴到 mermaid.live」。

### 证据输出

```text
agent 实际类型: CompiledStateGraph

图里到底有哪些节点:
 - __start__
 - model
 - tools
 - __end__

图里有哪些边:
 -  __start__ → model      (硬边)
 -      model → __end__    (条件边)
 -      model → tools      (条件边)
 -      tools → model      (条件边)
```

### 源码节选（精简，保留核心几行）

```python
graph = StateGraph(state_schema=resolved_state_schema, ...)
graph.add_node("model", RunnableCallable(model_node, amodel_node, trace=False))
if tool_node is not None:
    graph.add_node("tools", tool_node)
graph.add_edge(START, "model")
graph.add_conditional_edges("model", _make_model_to_tools_edge(...), ["tools", END])
graph.add_conditional_edges("tools", _make_tools_to_model_edge(...), ["model", END])
return graph.compile(checkpointer=checkpointer, store=store, ...)
```

### 教学要点

- **真实结构只有两个业务节点**：`model` 和 `tools`。前面画的 ReAct 循环图是一一对应的，不是抽象隐喻。
- **是否继续循环不是模型决定的**，而是 `_make_model_to_tools_edge` 决定的：看最后一条 AIMessage 是否还有 `tool_calls`。
- **`tools → model` 是条件边**：`return_direct=True` 的工具或结构化输出工具会跳过 `model` 直接到 `END`。
- **加 middleware 会让图变胖**：每个中间件钩子（`before_agent` / `before_model` / `after_model` / `after_agent`）都会被 `add_node` 进来，但骨架仍是同一条 ReAct 循环。这一节先埋一个伏笔，正式讲 middleware 留到后续小节或下一章。
- **体检流程**：遇到不熟悉的预构建 Agent，先用一张结构图建立整体心智，再 `print(agent.get_graph())` 的节点和边做证据对照，最后才去读源码——别让原始打印替代认知图。

## 4.6 create_agent 参数全景

### 要讲清楚的问题

到这里学生只接触了 `model`、`tools`、`system_prompt`。但 `create_agent` 真实签名有十几个参数，必须用一张分组表帮学生建立全景，并指出哪个是「扩展点本体」。

### 推荐演示

不需要新代码单元，直接用表格在 markdown 中呈现。重点是分组，不是逐字介绍：

| 组别 | 参数 |
|---|---|
| 必填两件套 | `model`、`tools` |
| 改 prompt / 输出形态 | `system_prompt`、`response_format` |
| 改 state | `state_schema`、`context_schema` |
| 接持久层 | `checkpointer`、`store`、`cache` |
| 调试与控制 | `debug`、`name`、`interrupt_before`、`interrupt_after`、`transformers` |
| 扩展点本体 | `middleware` |

### 教学要点

- 学生学完 LG-01～LG-04 已经能理解 `checkpointer`/`store`/`name`，这里只是把它们摆在一起。
- `interrupt_before=["tools"]` 是无 middleware 时最快的「工具前审批」开关；它的局限是「对所有工具一视同仁」。
- `middleware` 是本节后续重点；其它参数按需引用即可，不要一节课讲完全部。

## 4.7 middleware：把横切关注点从 prompt 里搬出来

### 要讲清楚的问题

学生最常见的反直觉点是：当 Agent 出了问题，第一反应是「加一句 prompt」。但「最多调 3 次」「带信用卡号要打码」「长对话要摘要」「危险工具调用前要问人」这些动作不是业务对话，是横切关注点。塞 prompt 不可靠。

middleware 的设计就是把这些动作变成图里真实的节点。

### 配图

可以暂时复用 4.5 节的「白盒化」结构图，文字补一句「middleware = 在 model 节点前后插的新节点」。如果后续要做精修配图，再单独画。

### 推荐演示

最小可运行 demo：`ModelCallLimitMiddleware(run_limit=1, exit_behavior="end")`。

```python
from langchain.agents.middleware import ModelCallLimitMiddleware

budget_agent = create_agent(
    chat_model,
    ops_tools,
    system_prompt=opsbot_prompt,
    middleware=[ModelCallLimitMiddleware(run_limit=1, exit_behavior="end")],
)
```

### 证据输出

```text
加 middleware 之后的节点:
 - __start__
 - model
 - tools
 - ModelCallLimitMiddleware.before_model
 - ModelCallLimitMiddleware.after_model
 - __end__

总消息数: 6
最后一条类型: ai
最后一条内容: Model call limits exceeded: run limit (1/1)
```

### 教学要点

- **middleware 不是装饰器，是真节点。** 它出现在 `get_graph()` 里、出现在 LangSmith trace 里，调试时一目了然。这一点直接呼应 4.5 节埋下的伏笔「为什么图会变胖」。
- **行为是被 middleware 阻断的，不是被 prompt 劝退的。** 即使 prompt 没说「只能调 1 次」，到第二次进 `model` 节点时 `before_model` 钩子已经决定退出。
- **按动机分类记忆内置 middleware**：
  - 限制次数：`ModelCallLimitMiddleware`、`ToolCallLimitMiddleware`
  - 重试 / 回退：`ModelRetryMiddleware`、`ToolRetryMiddleware`、`ModelFallbackMiddleware`
  - 上下文管理：`SummarizationMiddleware`、`ContextEditingMiddleware`
  - 安全合规：`PIIMiddleware`、`HumanInTheLoopMiddleware`
  - 工具体验：`LLMToolSelectorMiddleware`、`TodoListMiddleware`、`FilesystemFileSearchMiddleware`、`ShellToolMiddleware`
- 这一节**不展开 `HumanInTheLoopMiddleware`**，留给第 6 节的危险工具示例作为高潮，避免一次性塞太多 API。

## 5. 用 stream 观察黑盒内部

### 要讲清楚的问题

`invoke()` 只给最终结果，学生会觉得预构建 Agent 是黑盒。`stream()` 能看到每一步消息如何增长。

### 推荐演示

用 `stream_mode="values"` 打印：

- 当前 step。
- 最新消息类型。
- tool_calls 数量。
- 当前 messages 数。

### 教学要点

stream 的意义不是炫技，而是帮助学生看到：预构建虽然封装了图，但内部仍然是消息流、工具调用和循环路由。

## 6. 预构建的代价：快，但控制力少

### 要讲清楚的问题

要先破一个常见误解：**预构建 Agent 不是「不能审批、不能中断」。** 它自带 `interrupt_before=["tools"]`、`HumanInTheLoopMiddleware`、`checkpointer`（§4.6 / §4.7 已讲）。真正的代价，是核心状态以 messages 为主、复杂业务结构要自己搭——所以迁移触发点是「自定义状态 / 复杂路由 / 一等审计」，不是「要不要审批」。

### 配图

使用 `images/prebuilt-vs-custom-cn.svg`。注意图里 create_agent 一栏明确写了「也能中断 / 审批 / 持久化」，不要再说成预构建做不到审批。

### 推荐演示

定义危险工具 `issue_refund(order_id, amount)`，让默认 create_agent 直接执行退款，观察它**没有审批关卡就调用了副作用工具**。

### 证据输出

```text
危险工具是否被调用: 是
为什么这是问题: 默认 agent 直接执行了退款，中间没有任何审批关卡
最简修法（仍在预构建内）: interrupt_before=['tools'] + checkpointer，或 HumanInTheLoopMiddleware
需要更强控制时再迁移: 自定义 StateGraph —— 业务状态 / 复杂路由 / 一等审批审计
```

### 教学要点

- 不要用 prompt 代替安全边界（「请谨慎」不是边界）。
- 修复副作用工具**不一定要迁移**：先用预构建自带的 `interrupt_before` / `HumanInTheLoopMiddleware` 加审批关卡。
- 只有需要自定义业务状态、复杂路由、把审批 / 权限 / 审计做成一等显式结构时，才迁移到自定义 StateGraph。

## 7. 记忆与上下文：messages 会越来越长

### 要讲清楚的问题

预构建 Agent 的核心 state 是 `messages`。每次工具调用都会追加：

```text
HumanMessage → AIMessage(tool_calls) → ToolMessage → AIMessage(final)
```

这很方便，但长期对话会膨胀。

### 推荐演示

给 `create_agent` 加 `checkpointer`，用同一个 `thread_id` 连续对话。

### 证据输出

```text
第一轮 messages 数: N
第二轮 messages 数: M
第二轮是否接上同一 thread: 是
```

### 教学要点

这里衔接 LG-04：checkpointer 保存的是可恢复现场，不是长期偏好 Store。如果你需要长期用户资料、权限、审批状态，仍然要认真设计外层状态。

## 8. 多 Agent 预构建：把专家角色原子化

### 要讲清楚的问题

LG-05 讲过 tools 和 subgraph 的能力原子化；LG-06 继续往上一层：把一个专家 Agent 原子化。

### 配图

使用 `images/supervisor-swarm-cn.svg`。这张图沿用 §4.5 的「先整体、再拆解」节奏：① 先看两种拓扑（中心调度 vs 平级交接）；② 再拆一层「套娃」——每个专家就是图里的一个节点，而专家内部又是 §4.5 那张 model/tools 循环。

### 两种模式

| 模式 | 白话理解 | 适合场景 |
|---|---|---|
| `create_supervisor` | 一个主管调度多个专家 | 任务分发、结果汇总 |
| `create_swarm` | 多个专家平级交接 | 客服转接、连续接力 |

### 推荐演示

两种模式都要真跑一遍，而且**全流程 pretty_print**（不是只打最后一条），让学生看到任务怎么流转：

1. `supervisor`：建 `order_expert` / `refund_expert`，再用 `create_supervisor` 调度；`stream(stream_mode="values")` + 逐条 `pretty_print` 打全流程。
2. `swarm`：给两个成员各加一个 `create_handoff_tool`，用 `create_swarm(default_active_agent=...)`；同样全流程 `pretty_print`，观察对话被 `transfer_to_*` 从一个成员 handoff 到另一个。

两段之间各追加一个**白盒证据**：`print` 出 `get_graph()` 的节点，让学生看到主管 / 成员真的就是图里的节点——和上图「套娃」那层逐字对照。和 §4.5 一样：先给结构图建立心智，打印只作证据。

### 证据输出

```text
supervisor 图里的节点:
 - __start__
 - supervisor
 - order_expert
 - refund_expert
 - __end__

swarm 图里的节点:
 - __start__
 - order_member
 - refund_member
 - __end__
```

### 教学要点

- Supervisor 不是把所有工具塞给一个大 Agent，而是把专家角色原子化后交给主管调度。
- 别把多 Agent 当魔法：`create_supervisor` / `create_swarm` 编译出来同样是 `CompiledStateGraph`。所谓「多 Agent」，本质是把一张 ReAct 图当成一个节点，再用一张更大的图把它们连起来。

---

## 9. 什么时候从预构建迁移到自定义

| 需求 | 推荐选择 | 原因 |
|---|---|---|
| 3 天内做一个能查工具的 demo | `create_agent` | 标准循环，速度优先 |
| 多个专家角色由主管分配 | `create_supervisor` | 角色能力原子化，中心调度 |
| 客服在多个专家间平级转接 | `create_swarm` | 用 `active_agent` 保持当前负责角色 |
| 退款、重启、发布等副作用动作 | 自定义 StateGraph | 需要审批、权限、审计 |
| 需要 `user_role`、`risk_level` 等字段 | 自定义 StateGraph | 预构建核心 state 以 messages 为主 |
| 需要复杂业务分支 | 自定义 StateGraph | 不只是 ReAct 循环 |

一句话：**预构建负责把常见循环和角色调度封装好；自定义图负责把业务控制权拿回来。**

---

## 10. 常见误区

| 误区 | 现象 | 正确说法 |
|---|---|---|
| 用假函数模拟 Agent | 看不到模型如何真实产生工具调用 | 本节必须用真实 LLM |
| 以为预构建更高级 | 盲目替代自定义图 | 预构建只是封装标准循环 |
| 用 prompt 管危险工具 | 模型仍可能直接调用退款/发布工具 | 副作用工具必须有审批边界 |
| 把所有工具塞给一个 Agent | Agent 选择空间过大，难调试 | 复杂角色要原子化成专家 Agent |
| 把 supervisor 和 swarm 混用 | 不知道谁负责调度 | 任务分发用 supervisor，连续转接用 swarm |
| 忽略 messages 膨胀 | 长对话成本越来越高 | 用 checkpointer、裁剪、摘要、工具结果精简 |

## 11. 本节小结

学生应该能不用 API 名解释：

> 如果需求只是“模型判断工具、工具返回结果、模型再回答”，这是一条标准 ReAct 循环，可以先用预构建 Agent 快速验证。预构建的代价是中间状态、路由和审批不够可控；一旦业务需要显式状态、人工审批或复杂路由，就要迁移到自定义 StateGraph。

判断口诀：

```text
标准 ReAct → create_agent
主管分发专家 → create_supervisor
平级连续转接 → create_swarm
副作用审批 / 自定义状态 / 复杂路由 → 自定义 StateGraph
```
